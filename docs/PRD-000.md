# PRD-000: TPM-OS foundation

**Status:** Draft  
**Version:** 0.1  
**Scope:** Phase 1

## Executive summary

TPM-OS is an open library of modular professional skills for Technical Program Managers.

It does not require TPMs to adopt a single assistant, workflow, toolchain, or management style. Each skill performs a discrete function and can be adopted independently inside the TPM's existing way of working.

Phase 1 exists to prove that five carefully engineered skills can materially improve real TPM work.

## Problem

TPMs routinely work across incomplete information, competing priorities, complex stakeholder networks, and high-stakes communication. General-purpose assistants can generate plausible text, but they rarely provide a repeatable professional method with explicit inputs, validation, and known failure modes.

TPMs need trustworthy capabilities they can invoke when a particular job must be done well.

## Initial user

The initial user is a practicing TPM who:

- Runs their own AI sessions and preferred workflow
- Works across ambiguous, cross-functional programs
- Needs judgment support rather than generic document generation
- Must review and own every consequential output

## Product model

A TPM invokes a skill to perform one clearly defined professional function.

A skill may contain deterministic steps, AI reasoning, validation, and tools. Those implementation details remain subordinate to the skill's user-facing purpose.

TPM-OS augments the TPM. It does not prescribe how the TPM must operate.

## Phase 1 scope

Phase 1 contains exactly five skills:

1. **Session Bootstrap** — Establish the current working context, constraints, available evidence, and immediate objective.
2. **Program Bootstrap** — Turn an ambiguous or incomplete program into a structured starting point and first actions.
3. **OKR Builder** — Develop measurable, outcome-oriented objectives and key results from available context.
4. **Stakeholder Mapper** — Identify stakeholders, influence, decision rights, communication needs, and relationship gaps.
5. **Executive Review Builder** — Produce an executive-ready narrative and anticipate the questions leadership is likely to ask.

## Product principles

1. **Augment, do not constrain.** Skills must fit into the TPM's workflow.
2. **One skill, one professional job.** Scope must remain explicit and understandable.
3. **Determinism first.** Calculation, validation, state, and repeatable transformations belong in software.
4. **AI reasons.** AI is reserved for ambiguity, tradeoffs, synthesis, and communication.
5. **Human authority.** The TPM reviews and owns consequential decisions and outputs.
6. **Traceability.** Inputs, assumptions, reasoning boundaries, and validation results should be inspectable.
7. **Portability.** Models, runtimes, storage, and tools should remain replaceable.
8. **Pragmatic progression.** Quality standards guide product judgment; they do not become bureaucracy that prevents useful expansion.

## Definition of battle-hardened

A skill is battle-hardened only when it has:

- A specific user and job to be done
- Required and optional inputs
- A defined output contract
- A repeatable workflow
- Deterministic validation where possible
- Evaluation criteria and representative test cases
- Documented assumptions and failure modes
- Human review points
- Evidence from real TPM use
- Versioned changes informed by feedback

A polished response alone is not evidence of quality.

"Battle-hardened" describes a skill's maturity. It is not a prerequisite that every existing skill must reach before the product can explore or build another skill.

## Phase 1 success criteria

Phase 1 succeeds when:

- All five skills have complete specifications
- Each skill has representative examples and evaluation cases
- Each skill has been exercised against real TPM scenarios
- Users can invoke each skill independently
- Outputs are useful without requiring a TPM to abandon their preferred workflow
- Feedback demonstrates a material improvement over an unstructured AI conversation

## Non-goals

Phase 1 will not build:

- More than five skills
- A skills marketplace
- A proprietary agent runtime
- A monolithic TPM assistant
- Jira, Confluence, Slack, or other enterprise connectors
- A production knowledge graph
- Autonomous program management
- A large multi-agent architecture
- Organization-wide portfolio intelligence

These ideas may be revisited when product judgment, user feedback, and opportunity indicate that the current milestone is good enough to move forward.

## Implementation defaults

When implementation begins:

- TypeScript is the default language
- Interfaces and schemas are defined before framework choices
- Deterministic behavior is tested without an LLM
- AI providers are accessed through replaceable adapters
- No confidential or proprietary employer information is committed

## Governing question

For every proposed change, ask:

> Does this materially improve TPM work, and is it the best next use of our effort?

If the answer is no, deprioritize it.
